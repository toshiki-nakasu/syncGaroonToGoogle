# 文書の作成とレビュー

## READMEとdocsとAI指示の分離

配置はファイル数や行数ではなく、読者がその情報を使って何を判断するかで決める。AI向け文書は、コードや通常文書を読むだけでは見落としやすい暗黙知を明文化する場所とする。

| 種類 | 所有する情報 | 所有しない情報 |
| --- | --- | --- |
| `docs/README.md` | 領域の目的と担当範囲, 読む順序, 公開入口, 詳細への案内 | 詳細な仕様, 長い実行手順, 共通の変更規則 |
| `docs/`の目的名の文書 | 利用と保守のための仕様, 設計理由, 操作と検証の手順 | AIだけに向けた指示, 個別作業の経緯と進捗 |
| `AGENTS.md`, `docs/instructions/` | AIの作業規則, 誤判断しやすい点, 判断の理由, 変更の影響と確認先 | ファイル一覧, CLI操作一覧, 現行仕様や通常手順の再掲 |

恒久文書の入口は`docs/README.md`へ集約し、`docs/`の各フォルダにREADMEを追加しない。文書は次の場所へ分ける。

- 要件は`docs/requirements/`へ置く。
- 設計と構成は`docs/design/`へ置く。
- 操作手順は`docs/procedures/`へ置く。
- AI向け作業規則は`docs/instructions/`へ置く。

製品仕様と作業管理の記録を混在させない。

### 配置を決める順序

1. 想定読者と目的を一文で定める。異なる読者, 環境, 作業を無理に一文へまとめない。
2. 案内は既存の索引、人が使う設計と手順はdocs、AIが変更時に見落とす判断はAI指示へ置く。設計や構成の説明と操作手順は別文書にし、相互に参照する。
3. 同じ情報の所有文書を検索する。既にあれば追加先からリンクし、新しい正本を作らない。
4. 前提, 実行, 成功確認, 失敗時の扱いは一組の手順にする。手順の途中だけをREADMEやAI指示へ分散しない。
5. 親と同じ選択肢だけのREADMEは親へ統合する。単独手順しかないディレクトリでは目的名の文書を使う。独立した案内が必要な場合も、まずdocsの索引から目的別文書へ案内できるか確認する。
6. 統合後に無関係な説明を読ませないか確認する。たとえば検査を実行する手順と検査ツールを改修するための構造説明は分ける。READMEの削減数を完了条件にしない。

### 暗黙知をAI指示へ残す基準

「どの変更で」「何を誤りやすいか」「なぜ問題か」「何を確認するか」を具体的に書ける情報を残す。たとえば、ローカルの静的検査ではAWS上の権限や通信経路を保証できない理由と、別途確認する範囲がある。

暗黙知は推測で補わない。コード, 既存設計, 確認済みの作業記録を根拠にする。通常の保守者にも必要な設計理由と制約はdocsを正本とし、AI指示には変更時の落とし穴と参照先だけを残す。仕様の箇条書きを命令形に変えただけの再掲はしない。

共通の作業規則は保守指示と基本方針に一度だけ置く。一般的な言語解説, ツールの利用説明, 毎回更新が必要な値の一覧はAI指示へ増やさない。既存の自動検査で分かる項目を列挙するより、検査が見逃す点と確認先を示す。

仕様と手順はAI指示や作業記録を読まなくても利用できるようにする。AI指示からREADME, docs, 実装を参照し、通常文書からAI指示を仕様の根拠として参照しない。リンクの表示に必要な短い説明と、規則の重複は区別する。

## 重複を作らない

- 同じ意味の指示は一つの所有文書へ置く。言い換えや要約を別文書へ再掲せず、必要な見出しへリンクする。
- 複数対象に適用する規則は共通の所有文書へ集約する。AI固有の注意は対象の実装指示へ、利用者向けの操作は手順文書へ置く。
- 共通ルールを対象別文書で上書きしない。差分が必要なら適用条件を所有文書に明記する。
- 指示の追加と修正時は、関連文書を意味で照合し、重複, 矛盾, 古い参照を解消する。`docs/README.md`の案内も更新する。
- 文書と作業管理の境界は[文書と作業管理の分離](#文書と作業管理の分離)に従う。

## 構成と読者

- 最初に想定読者と目的を決め、読者が必要な操作と判断へ進める構造にする。
    - 設計では責務, 依存方向, 重要な不変条件, 判断理由を示す。
    - 操作手順では前提, 実行, 成功確認, 失敗時の扱いを示す。
- 利用者には操作と判断条件、開発者には変更に必要な責務と根拠を示す。不要な内部実装, 経緯, 繰り返す前提を削る。
- 段落は一つの論点を扱い、表は対応と比較に使う。要素の分け方は[情報の構造化](#情報の構造化)に従う。

## 情報の構造化

- 文の長さや項目数だけでなく、情報の役割で分ける。操作に対象, 確認条件, 条件付きの対処, 参照先が伴う場合は、短くても子項目や表で関係を示す。
- 親項目には操作や判断の要点を書く。子項目には、その親に属する具体的な情報を置く。
    - 複数の対象やコマンドは一つずつ列挙する。
    - 特定の対象だけに適用する確認条件や補足は、その対象の直下へ置く。
    - 条件付きの対処は「不足する場合」のように条件を明記し、操作や参照先をその下へまとめる。
    - 複数の参照先は一つずつ分け、何を確認するリンクか分かる表示名にする。
- 実行順序がある操作は番号付きリスト、並列の対象や確認条件は箇条書きにする。項目と値、状態と対処の対応を比較する場合は表を使う。
- 改行や句点だけで分割せず、何に対する条件や補足かを階層で示す。同じ階層には同じ役割と粒度の情報を並べる。
- 一つの操作だけで意味が完結する項目は短い一文でよい。各項目へ一律に「対象」「確認」などのラベルを付けず、必要な関係が分かる深さに留める。

たとえば、複数のコマンドと個別の確認条件、ツール不足時の参照先を含む手順は次のように分ける。

- before

    ```markdown
    1. ローカル端末で`bash --version`, `node --version`, `npm --version`を実行する。Node.jsは24系であることを確認する。不足する場合は[開発環境の構築](../../procedures/development-setup.md)を参照して準備する。
    ```

- after

    ```markdown
    1. ローカル端末でツールのバージョンを確認する。

        - 実行するコマンド
            - `bash --version`
            - `node --version`
                - 出力が`v24.`で始まることを確認する。
            - `npm --version`
        - ツールが不足する場合は、以下を参照して準備する。
            - [開発環境の構築](../../procedures/development-setup.md)
    ```

## 操作手順の書き方

- 手順を追加または変更するときは、[ユースケース一覧](../../procedures/use-cases.md)の実行者と作業カテゴリ、達成する目的を照合する。管理者とユーザーの操作を混ぜず、必要なら評価担当者や開発者の役割を分ける。作業上の役割を権限ロールの定義と取り違えない。
- ユースケースから各操作の見出しへ直接リンクする。文書の先頭だけへのリンクでは操作を選べない場合がある。見出し変更時は一覧も追従し、前提を飛ばして実行しない案内を保つ。検索評価へのリンクが文書アップロードから始まるなど、リンク先の最初の操作が実行者の責務を超えていないかも確認する。
- 手順がないユースケースは未整備と明記する。終了時の注意事項や設計上の制約だけがある場合も、実行手順があるとは扱わず、索引に未整備の範囲を示す。個人検証用のCLI手順があっても、認可や実行基盤を必要とする一般利用の手順が完成したとは扱わない。操作一覧はユースケース一覧へ集約し、各手順に同じ選択表を複製しない。
- 手順は上から読み進めながら実行と確認を繰り返すことで完了できる順序にする。後の節で初めて必要な入力や前提が判明する構成を避ける。
- 各段階には実行する操作と成功の確認方法を置く。失敗時は次へ進まない条件と確認先を短く示す。
- 設計理由や補足知識は設計文書へ分離する。更新や復旧が別の作業なら対応する文書へ案内しないまま新規構築の途中へ混在させない。
- 対話入力や分岐を含む長い処理と繰り返すCLI操作はスクリプトへ分離する。手順書には入力の準備と公開スクリプトの呼び出しを残す。単発の短いコマンドまで無理にラップしない。
- スクリプトは対象名やパスを引数で受け取るなど必要な範囲で再利用可能にする。手順の短縮だけを理由に汎用フレームワークを作らない。

## 文章と文言の共通ルール

文書, 画面の文言, 作業中の説明, 最終報告に適用する。

- 丸括弧は半角の`()`を使い、全角丸括弧は使わない。
- 自然な日本語を使う。開発者にも一般の読者にも使われない造語や、不自然な直訳と言い回しを避ける。専門用語は文脈に合う一般的なものを選び、読者に必要な説明を添える。
- 複数の文章を列挙するときは箇条書きにする。
- 要素の列挙も原則として箇条書きにする。本文や表のセルで短い名称だけを並べる場合は、5項目未満に限り`a, b`のように半角コンマと半角スペースで区切ってよい。個別の操作や確認が必要な要素は、項目数にかかわらず[情報の構造化](#情報の構造化)に従って分ける。
- 選択肢は`/`で区切る。
- 列挙の区切りに日本語の読点`、`や中点`・`を使わない。読点は列挙ではない通常の文章に限って使う。
- 箇条書きは半角ハイフンと半角スペースで始める。並列項目の粒度を揃える。
- 手順や順序を示すときは、番号付きの箇条書きにする。
- 一文に情報を詰め込みすぎず、長くなる場合は文を分ける。文章全体も必要な内容に絞り、重複や冗長な説明を省く。

## 文書と作業管理の分離

`work/`は削除可能な一時管理領域とする。恒久文書から配下の文書をリンクしたり、仕様や手順の根拠として参照したりしない。検証や通常の開発も、この領域の存在を前提にしない。

- 仕様, 設計理由, 操作手順はdocsの所有文書へ置く。未決の設計事項も、利用や実装の判断に必要なら対象の設計文書に残す。
- AI向け文書には[分離方針](#readmeとdocsとai指示の分離)に合う継続的な判断だけを書く。
- 個別作業の計画と進捗は`work/`へ置く。領域内の案内をREADMEにまとめても、他の文書からは参照しない。
- タスクはユースケースIDに対応付け、実装と操作手順、環境への反映と動作確認を別々に判定する。一部のCLI実装や設計文書の存在だけでユースケース全体を完了にしない。実環境の受入が残る場合は、その範囲を記録する。
- 対応付けの変更では既存タスクの完了条件と未確認範囲を引き継ぐ。共通作業を重複して起票せず、異常時の復旧や本番への復帰も対応するユースケースへ紐付ける。文書整理そのもののタスクは製品のユースケースと分ける。
- 完了時は継続して使う知識を所有文書へ統合し、統合先だけで利用と保守ができることを確認する。未完了の記録があれば状態を更新し、役割を終えた記録と参照を削除する。

## 表記と参照

- 日本語で具体的に書き、用語, 語尾, 表記を文書内で揃える。略語は必要なものだけ初出で説明する。
- パス, キー, コマンドはインラインコードにし、操作名, タスク名, 出力値は実装と一致させる。
- Markdownの各ブロックの前後に空行を置く。
- コマンドの実行場所を明記する。引数一覧と既定値はCLI help、運用値は設定を正本にし、本文に転記しない。
- 外部資料は関連する説明の近くから直接リンクし、どの仕様や判断の確認先か分かる文言にする。参照資料だけの一覧文書は作らない。
- 詳細の正本へ相対リンクする。仕様の説明を互いに委ね、どちらにも定義がない循環依存を作らない。索引への戻りリンクや関連手順の相互案内は許容する。planとapplyの間の確認や破壊的操作の中止条件を省略しない。
- 文書名の番号の接頭辞は読む順序が必要な文書群だけに付け、同じフォルダの同じ文書群で1から欠番なく揃える。追加, 移動, 削除では見出し番号と参照も追従する。独立した話題の文書には番号を付けない。
- `docs/`の追加と移動では`docs/README.md`と参照元を更新する。AI指示は実装指示の索引から辿れるようにする。
- 手順を分割するときは、移動した本文の同一文書内リンクと図中の文書パスも確認する。リンクが有効でも、別作業のサーバー起動や権限設定を要求していないか、各入口から前提と変数の準備を読み直す。表記変更で見出しのアンカーが変わる場合は参照も追従する。
- `.agents/skills/`はSkillの配置先。外部由来のSkillは明示されたupstream更新以外で編集せず、リポジトリ固有の整形と検査から除外する。

## 注意書き

補足や操作上の注意は、`yahyabatulu.vscode-markdown-alert`でプレビューできるGitHub形式のアラートを必要な箇所で使う。通常の説明や手順全体をアラートへ入れず、判断に必要な注意を対象の操作の直前に置く。

| 種類        | 用途                                 |
| ----------- | ------------------------------------ |
| `NOTE`      | 補足情報                             |
| `TIP`       | 任意の効率化や便利な方法             |
| `IMPORTANT` | 成立に必要な前提や見落とせない条件   |
| `WARNING`   | 操作による損失や不具合への注意       |
| `CAUTION`   | 取り消せない操作や重大な影響への注意 |

マーカーと本文の各行を`>`で始め、段落間の空行にも`>`を付ける。

```markdown
> [!WARNING] この操作は保存済みのデータを削除する。必要なデータを退避してから実行する。
```

## 変更時の内容レビュー

文書を追加または修正したら、作業者が変更後の文書を通読し、次をレビューしてから完了とする。lintやリンク検査の合格だけで内容レビューを代用しない。別エージェントの起動やユーザー承認を必須にはしない。

| 観点 | 確認すること |
| --- | --- |
| 構造 | 目的から詳細へ自然に進めるか。見出しの階層と順序が適切か |
| 文言と表記 | [文章と文言の共通ルール](#文章と文言の共通ルール)を満たし、一読で意味が伝わるか。曖昧な表現や用語の揺れがないか |
| 粒度 | 段落, リスト, 表の選択が内容に合い、並列項目の粒度が揃っているか。操作に対象や確認条件を詰め込まず、条件と参照先が対応する要素の下にあるか |
| 読者 | 不要な内部情報を削れているか。必要な前提や判断材料を省いていないか |
| 正確さ | 操作や参照先が実在し、通常文書に作業経緯, 進捗, 検証報告が混在していないか |
| 重複 | 同じ規則を別文書へ複製していないか。AI指示は[所有範囲](#重複を作らない)と整合するか |
| 配置 | READMEは案内、docsは仕様と手順、AI指示は暗黙知と作業規則を所有し、必要な固有情報を移管できているか |

レビュー結果と必要な修正は最終報告へ短くまとめる。継続作業がある場合は作業記録にも残し、[文書と作業管理の分離](#文書と作業管理の分離)に従って整理する。機械的な検証コマンドは[ローカル検証](../../procedures/development-procedures.md#ローカル検証)を使う。
