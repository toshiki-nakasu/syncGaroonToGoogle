# Chrome拡張機能のテスト設計

保守担当者が、変更した責務に対応するテストと確認範囲を選ぶための設計です。実行方法は[開発と検証](../procedures/development-procedures.md#ローカル検証)を参照してください。

## 確認する境界で分ける

| 配置 | 確認すること | 差し替える境界 |
| --- | --- | --- |
| [test/unit](../../chrome-extension/test/unit/) | 検証対象の部品が公開する動作 | 対象部品の依存先だけ |
| [test/ui](../../chrome-extension/test/ui/) | 画面上の入力から結果表示まで | DOMの一部とWorkerへの応答 |
| [test/usecases](../../chrome-extension/test/usecases/) | アプリケーションを通した操作の完了と再開 | Chrome APIと外部サービス |
| [test/browser](../../chrome-extension/test/browser/) | 実Chromiumでのモジュール読込と画面操作 | Google認証とCalendar API |
| [test/support](../../chrome-extension/test/support/) | テスト環境と入力データの共通部分 | 検証対象として扱わない |
| [script/test](../../script/test/) | 配布処理と文書検査 | Gitの送信先とGitHubのHTTP応答 |

単体テストは本番コードと対応するフォルダーに置きます。APIクライアントのテストに同期処理の期待値を持ち込まず、画面のテストへ削除計画の規則を複製しません。

## 共通の環境

保存領域は値をコピーして変更を通知します。辞書のキー順も並べ替えるため、メモリー上のオブジェクト参照と保存後の値を混同しません。

Chrome境界ではアラームと接続先の状態をテストごとに作ります。アプリケーションを作り直す場合も、保存領域と外部サービスの状態は同じものを使います。これによりWorker再起動後の再開を確認します。

Calendar APIの代替実装は、ユースケースが使う応答だけを提供します。

- 予定の一覧と個別取得
- 予定の書き込み
- 既存の予定と削除済みのIDへの衝突
- ETagの不一致

未知の呼び出しを空の成功応答にしません。

グローバル変数の差し替えは共通の後処理で元へ戻します。予定と設定の入力はケースごとに作り、前のケースの変更を次の前提にしません。

## ケースの独立性

一つのケースは一つの目的を確認します。設定保存から停止と再開までのように、同じ目的に必要な操作順は一緒に扱います。前のケースの成功や予定件数の累積には依存しません。

競合の確認では、API応答をPromiseで待たせて実行順を決めます。任意のミリ秒数を待って処理が終わったと推測しません。画面の非同期表示だけは条件の成立を期限付きで待ちます。

同期済みのGoogle予定を作るfixtureと、項目変換の正解を区別します。変換を確認するテストの期待値は固定の値にし、検証対象の変換関数から正解を生成しません。

## 残す観点と扱わない観点

| 残す観点                   | 理由                                         |
| -------------------------- | -------------------------------------------- |
| 同じ識別子の再同期と移動   | 重複作成と予定の欠落を防ぐ                   |
| 停止中と全削除中の操作     | 誤った再開と並行書き込みを防ぐ               |
| 取得失敗と更新されたETag   | 不完全な情報から予定を削除しない             |
| 保存領域を通した確認と再開 | Chrome固有のキー順とWorker終了を考慮する     |
| 画面から届く操作と失敗表示 | 実行前のエラーを利用者が確認できるようにする |

HTML中の要素の並びとCSSクラス名だけを正解にする検査は行いません。描画上の見た目も単体テストの対象にしません。ユーザーが操作できるかと、結果を読めるかで確認します。

## 実ブラウザーとの境界

配布処理のBashテストはZIPの実際の内容と各ファイルのハッシュを確認します。タグは一時Gitリポジトリへ作成し、ローカルのbareリポジトリへ送ります。開発リポジトリとGitHubへタグを送信しません。

PowerShellの更新テストは生成済みZIPを使い、HTTP境界だけを差し替えます。ファイルの置き換え、不要ファイルの削除、同じ版の修復、破損ZIPの拒否を実ファイルで確認します。会社端末の実行ポリシーと実際のGitHub認証は別途確認します。

Windows PowerShell 5.1のZIP生成処理は、項目名に`\`を使う場合があります。テストでは実行OSによらずそのZIPを明示的に生成し、`/`形式の配布ZIPと両方を扱えることを確認します。区切り文字が混在する重複項目と、親参照を含む不正パスも拒否することを確認します。

Node.jsのUIテストは、必要なDOM操作だけを代替しています。この層だけでは、次の動作は保証できません。

- Chromeの描画とダイアログの挙動
- 実アカウントの権限
- タブ内の通信

入口のイベント登録と、モジュールの読み込みを含む確認は[ブラウザーテスト](../../chrome-extension/test/browser/Extension.test.js)で行います。導入方法は[開発環境の構築](../procedures/development-setup.md)、実行方法は[実ブラウザーでの確認](../procedures/development-procedures.md#実ブラウザーでの確認)を参照してください。API応答を差し替えたChromeテストと、実サービスへの接続確認は区別します。
